S1. Clean architecture with practical naming
    Feature-first layout (screens/providers/models/repositories) with no
    Clean Architecture jargon (no data/domain/presentation). Easy to navigate.

S2. Fail-closed design in return allocation
    Pool extras are all-or-nothing: if any of homeHold, overflowConfirmed,
    overflowRemaining is missing, all are treated as null. The UI gracefully
    hides the extra info rather than showing partial/wrong data.

S3. Offline-first for batches with proper sync queue
    OfflineFirstBatchRepository with CacheService + SyncQueueDao + SyncManager
    is production-grade for the batch entity. Negative temp IDs for offline
    creates, rollback on failed deletes — well implemented.

S4. WebSocket session security
    D2D WebSocket sends sessionid + csrftoken via Cookie header on connect.
    Backend rejects with close codes 4401 (unauthorized) and 4403 (forbidden).
    Flutter handles both gracefully with user-facing error messages.

S5. Optimistic delete with rollback in BatchProvider
    deleteBatch() removes from UI immediately, calls API, and rolls back on
    failure. Good UX pattern.

S6. Error message surfacing pipeline
    Backend → Dio → ApiExceptionHandler → ApiResult.failure → Provider →
    SnackBar. The new _statusMessage error handling (M7) correctly passes
    server-side rejection messages to the user. No silent failures.

S7. Comprehensive model tests
    return_available_model_test.dart and return_batch_status_model_test.dart
    cover: split parsing, flat-payload rejection, missing keys, partial extras
    fail-closed, zero-value extras. D2D trip-ended detection covers both
    camelCase and snake_case payloads.

S8. Documentation discipline
    PROJECT_BRAIN.md, DOC_REGISTRY.md, PROJECT_TODOS.md, and the roadmap
    are all consistently updated per session. Session handoff log is practical.

C1. add_commuter error response lands in SUCCESS path, not FAILURE
    Severity: HIGH
    File: return_batch_repository_impl.dart, lines 92-104

    When the backend returns { status: "error", message: "not eligible" }
    with HTTP 200, the code currently does:
      return ApiResult.success(_statusMessage(response, ...))

    This means the provider calls _runAction(), sees isSuccess, then calls
    loadReturnTrip() to reload. The "error" message appears in a SnackBar
    as a SUCCESS message string, but the state is treated as if the action
    succeeded. The full reload will show the commuter is NOT confirmed
    (so no data corruption), but:
    - The SnackBar text says "not eligible" after a SUCCESS result — confusing
    - loadReturnTrip() is called unnecessarily (3 API calls wasted)
    - If the backend returns HTTP 200 + { status: "error" } for add_commuter,
      the Flutter side should treat it as a failure, not success.

    RECOMMENDATION: If _statusMessage detects status == "error", return
    ApiResult.failure instead of ApiResult.success. Alternatively, check
    status == "error" before wrapping in success.

    NOTE: If the backend returns HTTP 4xx for rejections (409, 400, etc.),
    this issue is mitigated because the catch block would handle it. Verify
    which HTTP status validate_add_commuter() returns. If it's 200 with
    error in the body, this is a real bug.

C2. POST /user/ still trusts client userType
    Severity: HIGH (security)
    File: Backend (cts-docker), not Flutter — but Flutter disabled sign-up.

    Public self-registration is disabled (redirect /signUp → /signIn), BUT
    the backend endpoint POST /user/ still accepts a userType field from the
    client. A direct curl/Postman call could create an ADMIN account.
    This is documented in PROJECT_TODOS but remains unfixed.

    RECOMMENDATION: Backend must reject any userType other than COMMUTER on
    public POST /user/, or require admin auth for DRIVER/ADMIN creation.

C3. No retry/reconnect logic for D2D WebSocket
    Severity: MEDIUM-HIGH
    File: d2d_channel_provider.dart

    If the WebSocket connection drops due to a transient network issue (not
    4001/4401/4403), the user sees "Live connection failed" and must manually
    navigate away and back. There is no automatic reconnect with exponential
    backoff.

    RECOMMENDATION: Implement a reconnect strategy (e.g., 3 retries with
    1s/2s/4s delays) for non-terminal close codes. Terminal codes (4001,
    4401, 4403) should NOT retry.

M1. Return batch operations are not offline-capable
    Only batches CRUD has offline-first support. Return batch confirm/remove/
    end are pure REST with no queue. If a driver is in a low-connectivity
    area during the evening return, actions will silently fail.

    RECOMMENDATION: At minimum, show a clear "You are offline" message before
    attempting return batch actions. Full offline queue can be deferred.

M2. No loading/disabled state during confirm/remove API call
    File: return_batch_commuter_screen.dart

    actionInProgress disables the Slidable action, but the user can still
    switch tabs and trigger another action on the other tab. There is no
    debounce or queue — two rapid swipe-confirms could race.

    RECOMMENDATION: Disable both tabs' actions while actionInProgress is true
    (already done via the actionInProgress flag — verify it covers both tabs).
    Consider adding a brief local optimistic move of the commuter between
    lists before the API response.

M3. ReturnBatchProvider is a singleton — stale data across batches
    File: return_batch_provider.dart

    The provider is app-scoped (registered once in AppProviders). When the
    admin opens Batch A's return list, then goes back and opens Batch B,
    the old Batch A data briefly flashes before loadReturnTrip replaces it.

    RECOMMENDATION: Call clearActiveBatch() on screen dispose, or set state
    to loading before any data is rendered when batchId changes.

M4. 47 packages have newer versions available
    flutter pub outdated shows 47 upgradable packages. Some are security-
    relevant (dio, firebase_core, flutter_secure_storage, permission_handler).

    RECOMMENDATION: Schedule a dependency update sprint. At minimum, update
    dio (5.10→5.11), flutter_secure_storage (10.3→11.0), and firebase_core.

M5. Batch-08 is still LIVE from QA (DTODLOG 10, WS /ws/11/)
    The lab QA session left Batch-08 in a LIVE state. This could interfere
    with future testing if not cleaned up.

    RECOMMENDATION: Run admin End or manually clear the Redis key + DTODLOG.

M6. ReturningBatchScreen GridView card has SingleChildScrollView inside
    File: returning_batch_screen.dart, line 111

    Each grid card wraps its content in SingleChildScrollView. If the
    childAspectRatio (0.68) is too small for the content (especially with
    pool extras showing 3 extra InfoRows), the card becomes scrollable
    inside a scrollable grid — poor UX on small screens.

    RECOMMENDATION: Use a dynamic aspect ratio or switch to a ListView with
    fixed-height cards when pool extras are present.

L1. SnackBarService.showsSuccessSnackbar called from repository layer
    File: batch_repository_impl.dart

    The repository layer (data/network) should not directly show UI elements.
    SnackBar calls should happen in the provider or screen layer only.

L2. AppManager.instance static globals
    AppConfig and AppManager use static singleton patterns. This makes
    testing harder and couples business logic to global state.

L3. Legacy re-export stubs still exist
    Phase C/D of the migration (collapse legacy root folders, rename
    *_controller.dart files) is pending. Some import paths still go through
    stub re-exports.

L4. No widget/integration tests for screens
    Only model-level unit tests exist (11 total). No screen rendering tests,
    no integration tests, no golden tests. The default widget_test.dart is
    a smoke test only.

L5. D2dChannelProvider shared between admin and driver
    Both D2dChannel (admin) and D2DLogScreen (driver) use the same
    ChangeNotifier instance. If somehow both are mounted simultaneously
    (unlikely in practice due to role guards), they would interfere.

L6. No rate limiting on return batch confirm/remove
    A rapid-tapping user could fire many POST add_commuter calls before
    the provider reloads. Backend atomicity (Redis SADD) prevents double-
    confirm, but it wastes bandwidth and may confuse the user.

L7. ConnectivityService._lastOnline can be stale
    The cached value is only updated on connectivity change events. If the
    device connects before the listener is set up, _lastOnline stays null
    until the first event. The _refresh() fallback handles this, but there
    is a window where isOnline awaits unnecessarily.

L8. offline_temp module still exists as prototype
    The offline_temp/ folder is a separate prototype that is not integrated
    into the main feature modules. It should be merged or isolated per
    Phase E of the migration plan.

SECTION 6: EDGE CASES & "IMPOSSIBLE" SCENARIOS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

E1. Race: Two admins confirm the last overflow seat simultaneously
    Scenario: overflowRemaining=1. Admin A and Admin B both swipe-confirm
    different overflow commuters at the same moment.
    Backend: Redis SADD is atomic per key, but validate_add_commuter reads
    remaining before SADD. If both read remaining=1, both succeed, and the
    cab is overbooked by 1.
    RECOMMENDATION: Use Redis WATCH/MULTI or Lua script for atomic
    check-and-add. Verify backend implementation.

E2. Driver STOP while admin is adding commuter on D2D channel
    Scenario: Driver sends STOP; admin simultaneously sends ADD.
    If STOP closes the group before ADD is processed, ADD fails silently
    (send on closed socket is swallowed per code comment). But if ADD
    is processed just before STOP, the commuter is added to a trip that
    immediately ends. The commuter's isComing state may be inconsistent.
    RECOMMENDATION: Document this as a known race. Backend should reject
    ADD after STOP flag is set.

E3. Backend returns HTTP 200 with status "error" for add_commuter
    (See C1 above.) If the backend's validate_add_commuter returns
    200 + { status: "error", message: "..." }, Flutter treats it as
    success. If it returns 400/409, the catch block handles it properly.
    VERIFY: What HTTP status does validate_add_commuter return?

E4. User switches role mid-session (e.g., admin account reconfigured)
    SessionAuthNotifier caches userType from session storage. If the backend
    changes a user's role (e.g., DRIVER → ADMIN), the app won't know until
    the next login. GoRouter redirects would send them to the wrong home.
    RECOMMENDATION: Low priority — admin-initiated role change is rare.
    Consider refreshing session on app resume from background.

E5. Timezone mismatch: server midnight vs device midnight
    CList and return allocation are day-scoped. If the server is in UTC and
    the device is in IST (+5:30), the "day" boundaries differ by 5.5 hours.
    A commuter confirming at 11 PM IST may be on "tomorrow's" server day.
    RECOMMENDATION: Verify backend uses consistent timezone for day scoping.

E6. WebSocket reconnect after phone sleep/resume
    If the phone sleeps during an active D2D trip, the WebSocket closes.
    On resume, the user sees a stale list. There is no auto-reconnect
    or "Connection lost — tap to reconnect" banner.
    RECOMMENDATION: Listen to AppLifecycleState.resumed and reconnect.

E7. Return batch end while driver has confirm in-flight
    Admin ends return trip (POST end/<batchId>) while driver's confirm
    POST is still in flight. The confirm may succeed (race) or fail.
    If it succeeds, the commuter is confirmed on an ended trip.
    RECOMMENDATION: Backend end should clear the Redis set atomically
    and reject any concurrent add.

E8. Overflow commuter's home batch STOP hasn't fired yet
    Rule R9 says a student enters the eligible set only after their morning
    STOP. But the current overflow-confirm UI shows them if they're in
    the view/ response. If the backend view/ correctly filters by CList
    attendance, this is safe. If not, a non-eligible overflow commuter
    could be confirmable in the UI.
    VERIFY: Does GET view/ filter by CList attendance?

E9. Large org with 50+ batches — picker screen performance
    ReturningBatchScreen fires fetchStatusesForBatches for ALL batch IDs
    in parallel (Future.wait of N API calls). With 50 batches, that's 50
    concurrent HTTP requests. This could overwhelm the backend or hit
    connection limits.
    RECOMMENDATION: Paginate or batch the status calls (e.g., 10 at a time).

E10. Session cookie expires while on return commuter list
     If the session expires during a long return-trip management session,
     the next confirm/remove call returns 401. The global 401 handler
     clears the session and refreshes auth notifier, which triggers router
     redirect to /signIn. But the ReturnCommuterListScreen is still mounted
     and may show a confusing error before the redirect fires.
     RECOMMENDATION: Low priority — 401 handler already covers this. The
     brief error flash is cosmetic.

SECTION 7: R4 RELAXATION IMPACT ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The R4 rule change (earlier-only → any-direction) has these implications:

7.1 Overflow definition changed
    OLD: Overflow = students whose home returnTime is STRICTLY LATER.
    NEW: Overflow = any non-home eligible student (regardless of direction).
    The roadmap section 3 still says "home.returnTime > D.returnTime" in
    the overflow definition. This is now inconsistent with R4.
    RECOMMENDATION: Update roadmap Phase 2 allocator description.

7.2 Seat math unchanged (good)
    home_hold still reserves seats for home-batch riders. remaining still
    equals capacity - home_hold - overflow_confirmed. The direction of
    overflow doesn't change the math — only who qualifies as overflow.

7.3 UI impact: none needed
    The Available tab already shows Home then Overflow. The overflow section
    will now include commuters from earlier batches too, but the UI doesn't
    distinguish direction — it just shows the name/POP/batch. This is fine.

7.4 Backend must update overflow eligibility filter
    GET view/<id> must now return ALL non-home eligible commuters as overflow,
    not just those with later returnTime. VERIFY this was updated in
    cts-docker alongside the R4 relaxation.

7.5 Test coverage gap
    The Flutter tests don't test R4 direction. The backend tests
    (test_return_allocator.py) should have a case for earlier→later overflow.
    VERIFY: Does the backend test suite cover bidirectional overflow?
